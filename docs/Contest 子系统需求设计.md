# Contest 子系统需求设计

## 1. 业务边界

Contest 负责对局编排、赛果复核、整场结算及初赛排名。Portal 受理天梯和决赛请求并公示结果。Arena 根据 Contest 下达的任务固定版本、构建运行 Bot 并发布单局归档。服务间使用本机 HTTP 和 UTF-8 JSON。

| 交接内容 | 契约 |
| --- | --- |
| 对决提交 | `POST /contest/v1/duels` 接收 `duel_id`、`rules`、`sides` 和可选的 `map_seed`。种子为整数或 `random` 时使用天梯地图，省略或指定同名赛段时使用正式地图池。按原编号和内容幂等受理，返回空体 `202` |
| 对决查询 | `GET /contest/v1/duels/{duel_id}/status` 返回 `in_progress` 或 `finished`。`GET /contest/v1/duels/{duel_id}/result` 返回 `side_results` 和 `result`，待定时双方为 `pending`、`result` 为 `null`。结算后提供登记胜负局数和按局序排列的生效 `runs`、`games`，天梯另有开局时间、确认时间及同赛段前序对决编号 |
| 初赛文件 | 导入「队伍」工作表的「队伍编号」「队名」。主办方确认全部赛果后导出「排名」「对决」「对局」。表格用固定值，编号为文本，局数、局序和名次为整数 |
| 单局执行 | `POST /arena/v1/runs` 下达 `run_id`、`duel_id`、`rules`、按出生点排序的 `bots` 及 `config.map`，地图提供整数 `seed` 或已封存的 `file` 文本和 `sha256` |
| 执行查询和运行监控 | `POST /arena/v1/runs/query` 查询一个或多个执行，已受理的状态放在 `runs`，未知编号放在 `missing_run_ids`。执行状态为 `queued`、`running`、`finished`、`build_failed` 或 `platform_error`，仅平台故障状态带 `reason`。`GET /arena/v1/status` 查询槽位、队列与近期完成和故障次数 |
| 单局归档 | 终态可查时从共享根目录的 `runs/<run_id>/` 读取归档。完成局包含 `match.json`、`replay.json`、`log.jsonl`，构建失败读取 `match.json` 中的双方构建结论 |

对决编号匹配 `duel-[A-Za-z0-9_-]+`，执行编号匹配 `run-[0-9]+\.[1-9][0-9]*`。参赛队伍编号为 `team` 加三位数字。正式对决双方均为队伍，天梯最多包含一个基准 Bot（`bot001`、`bot002`、`bot003`）。`rules` 取 `prelim` 或 `final`。

Portal 收到的查询响应带 `Cache-Control: no-store`。无效对决编号返回 `400 INVALID_DUEL`，未知编号返回 `404 DUEL_NOT_FOUND`。提交时，同编号不同内容返回 `409 DUEL_CONFLICT`，正式地图池未配置返回 `503 MAP_POOL_UNAVAILABLE`。

结算 JSON 的 `outcome` 为 `win`、`draw` 或 `double_loss`，`winner` 为胜方编号或 `null`。登记局数按参赛方编号保存为 `games_won`、`games_lost`。`games` 的每项含 `ordinal`、`run_id`、`winner` 和按参赛方编号给出的 `score`，经人工裁定的单局另附 `reason`。累计指标决胜时附 `tiebreak`，构建判罚附 `build_run_id`，整场人工裁定附 `reason`，决赛资格判负另附 `forfeited`。天梯结果附带 `started_at`、`ended_at` 和按确认顺序排列且去重的 `previous_duel_ids`，前序取双方各自同赛段的上一场已确认对决。

初赛结果工作簿的输出列固定如下。缺失的胜方或构建判定编号用空单元格。

| 工作表 | 按序排列的表头 |
| --- | --- |
| 排名 | 名次、队伍编号、胜局数、负局数 |
| 对决 | `duel_id`、队伍1编号、队伍2编号、队伍1胜局数、队伍1负局数、队伍2胜局数、队伍2负局数、整场结果、胜方、判定原因、`build_run_id` |
| 对局 | `duel_id`、预定局序、`run_id`、胜方、裁定理由。每个生效单局一行，保留尝试后缀，自动决胜时裁定理由留空 |

## 2. 对局编排

Contest 在同一事务中保存对决、预定局和首次执行尝试。对决计划确定后，固定地图、局序和出生点分配。天梯使用一个固定的实际种子打两局，正式对决依次使用相应赛段的三张封存地图，每张两局。每张地图的首局按 `sides` 分配出生点，第二局换边。

各类赛事在互不重叠的执行时段调度。天梯按 Portal 下达顺序编排，初赛可并行推进不同对决，决赛按场串行。同场的下一局须等前局复核生效后提交。压测使用独立批次，赛果和进度与正式赛事隔离。

初赛名单由 Portal 按截止时已报名且 `main` 分支上有代码的队伍生成，编排后冻结。名单内队伍两两对决一次。退赛时保留已完成的对决，尚未开始的场次按整场判退赛方负。排名依次按登记胜局数降序、负局数升序、队伍编号升序排列。主办方确认全部赛果后才能导出结果。

## 3. 执行、复核与结算

### 3.1 执行记录

单局提交、状态查询和归档复核分别推进，网络请求在数据库事务外执行。Contest 按当前尝试关联终态及归档。写锁暂不可用时，服务等待锁释放再完成对应事务，保留已收到的 Arena 响应。已查询的终态持久化后进入复核队列，服务重启后可继续处理。

发送中、已受理、交付未确认和已申请按原编号补发的当前尝试占用对应的调度阶段，直到复核记账或对决关闭。Arena 明确拒绝的提交保留在主办方待处理记录中，释放调度阶段。

查询对象为已受理或提交未确认、尚未取得终态的当前尝试。正式初赛和独立压测共用 10 秒一轮的查询，每批最多 100 个 `run_id`，上一轮未结束时跳过本次触发，失败批次留待下一轮。天梯和决赛每次传一个编号，返回 `queued` 或 `running` 后至少等待 0.5 秒再查，失败后退避重试。终态按编号核对后落库，已经重跑替换的尝试保留原记录。 [Arena 批量查询示例](<Arena 与 Contest 对接说明.md#31-批量查询>)

### 3.2 赛果复核

1. 核对 `match.json` 中按出生点排列的 `bots[].team_id` 与请求一致，队伍的 `commit` 有效，地图编号和哈希与计划一致。同场版本按参赛方归队核对，天梯的 `duel_started_at` 须在同场各局保持一致并带 `+08:00`。
2. 对已完成的单局，核对归档版本与当前引擎版本，按回放命令和公开观测重算并核对 `match.json` 及裁判日志。复核包括开局、响应状态、退出事实、整数微秒计时和技术判负。
3. 证据缺失、不一致或版本不受支持时，记录原因并暂缓生效。证据通过复核且四项指标全同时，当前尝试进入待裁定。每个预定局至多采纳一个复核通过且胜方明确的执行。

### 3.3 整场结算

正常对决按局序汇总有效执行，胜局数多者胜。天梯各赢一局时记平局。正式对决各赢三局时，按各局出生点与队伍的映射归队，依次比较六局累计 `score`、`bonus`、`lead_turns`、`time_us`。前三项取较高值，耗时取较小值，四项全同则暂缓结算。

整场判罚时按预定局数登记，天梯为 2 局，正式对决为 6 局。单方构建失败或决赛资格判负时，该方记全部负局，对手记全部胜局。双方均判负时各记全部负局，胜方为空。判罚前已生效的单局继续保留。

Contest 在同一事务中保存单局复核结论和由此确认的整场结算。查询从同一读事务取得整场结果与生效单局明细。

## 4. 主办方管理

后台支持正式名单导入、单循环编排、进度与 Arena 运行状态查询、人工裁定、独立压测、赛果确认和导出。`host`、`port` 设置监听地址和端口，默认端口为 `8082`。`admin_user` 与 `admin_password` 成对配置，均为 `null` 时关闭后台。`ip_whitelist` 按 TCP 来源匹配 IP 或 CIDR，`null` 放行所有来源，空数组拒绝所有来源。允许的来源仍需通过后台账号认证，写操作带 `X-Contest-Admin: 1`。

发生平台故障时，Contest 记录原因，作废受影响的尝试并暂停结算。主办方按 `run_id` 核对并排除故障后发起重跑。新尝试递增后缀，沿用同场固定的提交、地图、出生点和天梯开始时间，原尝试的归档继续保留。

在 `contest/` 可用 `python -B -m service --config <服务配置文件>` 执行人工操作。追加 `resend <run_id>` 按原编号和内容补发交付未确认或被拒绝的任务，`void <run_id> <原因>` 作废执行，`retry <run_id>` 为已作废的执行创建下一次尝试，`recheck <run_id>` 重新复核暂缓生效的归档。

### 4.1 四项全同时的人工裁定

主办方从待裁定列表选择复核通过但未决胜的当前单局，或六局均已生效且累计全同的正式对决，从双方参赛方中选择胜方并填写理由。单局裁定使当前尝试生效并允许同场下一局下达。整场裁定保持六局和已登记的 3∶3，直接确认整场胜方。操作、胜方、理由、操作人和时间在同一事务中保存，原始归档继续用于复核。重复提交相同胜方和理由返回同一条裁定，不同内容返回冲突。

`GET /admin/rulings` 列出待裁定项目。`POST /admin/rulings` 接收 `scope`、`target`、`winner`、`reason`，其中 `scope` 为 `game` 或 `duel`，`target` 为相应的 `run_id` 或 `duel_id`。命令行使用 `rulings` 与 `rule <game|duel> <编号> <胜方> <理由>`。

### 4.2 决赛资格判负

晋级名单确认后，Portal 将退赛或被取消资格的队伍及所在场次告知主办方。主办方对该队当前、或双方已确定的下一场未结算决赛录入资格判负。场次由 Portal 按固定对阵图提交并取得 `202`；缺位处理仍由 Portal 按赛事规章执行。主办方可选一方或双方并填写理由，Contest 立即按 6 局结算，保留此前已生效的单局和原始归档。

| 接口 | 请求及响应 |
| --- | --- |
| `GET /admin/final/forfeits` | 返回 `200` 和 `duels` 数组，包含每场未结算正式决赛的 `duel_id` 与 `sides` |
| `POST /admin/final/forfeits` | 接收 `duel_id`、`defeated` 数组和 `reason`。返回 `200` 和裁定记录，字段为 `scope`（`forfeit`）、`target`（对决编号）、`forfeited`、`winner`、`reason`、`operator`、`decided_at` |

例如提交 `{"duel_id":"duel-1902","defeated":["team003"],"reason":"队伍确认退赛"}`。判负队伍须为本场双方中的一支或两支，且互不重复。相同队伍集合与理由可重复提交并取得原裁定。修改已录入的裁定、对已结算场次或天梯场次操作返回 `409`。理由为空或队伍无效返回 `400`，未知对决返回 `404`。

Contest 同时关闭该场的剩余提交、查询、复核和裁定，丢弃关闭后才返回的响应。Portal 继续调用原有查询接口，取得 `finished`、登记局数、`forfeited`、`reason` 及已生效的单局明细。

### 4.3 独立压测

主办方在后台上传含至少两支有效队伍的 XLSX，使用 `load-` 加 1 至 40 位字母、数字、下划线或连字符作为批次编号。Contest 按初赛地图池编排真实的单循环，每场六个预定局，使用与正式初赛相同的提交、查询、复核和重跑机制。提交同一编号和名单可继续查看原批次，换一份名单须使用新编号。

压测进度按批次显示已结算场次、重跑、待处理记录、用时和每分钟结算场次。压测安排在与正式初赛和决赛分开的测试时段。压测数据通过后台访问，正式排名、确认、XLSX 导出和 Portal 查询均以正式赛程为准。

| 接口 | 请求及响应 |
| --- | --- |
| `GET /admin/load-tests` | 返回 `batches`，每项含 `batch_id` 和 `planned_at` |
| `POST /admin/load-tests/{batch_id}` | 用含「队伍」工作表的 XLSX 启动批次，返回批次进度 |
| `GET /admin/load-tests/{batch_id}` | 返回批次进度 |
| `POST /admin/load-tests/{batch_id}/retry` | 接收 `{"run_id":"run-12.1"}`，为本批次内已作废的尝试创建下一次执行，返回含 `retry_run_id` 的进度 |
| `POST /admin/load-tests/{batch_id}/stop` | 空请求体，结束当前批次，返回 `200` 和最终进度。已结束或已全部结算的批次可重复调用并取得原进度 |

全部场次结算时状态为 `finished`，记录 `finished_at`。主办方提前结束时状态为 `stopped`，记录 `stopped_at`，按该时间固定用时与吞吐量。未结算的场次计入 `duels.cancelled`，其中未生效的预定局计入 `games.cancelled`。Contest 保留已有结果和尝试记录，停止该批次余下的调度、查询、复核、重跑和裁定。

## 5. 交付

Contest 交付可在 Linux 上用 CPython 3.9.11 启动的服务和管理后台、各赛段裁判镜像及对应引擎版本。镜像交付时附标签和 digest。裁判读取只读的 `/task/task.json`，任务包含 `run_id`、`rules`、`config` 和按出生点排序的 Bot HTTP 根地址，向 `/out` 写出 `result.json`、`replay.json` 和 `log.jsonl`。

Contest 在配置的 `db` 路径初始化当前 SQLite 结构，所在目录须支持 SQLite WAL。Arena HTTP 地址和共享归档沿用现有部署配置。

选手材料包随赛段独立发布，包含同版引擎、Bot SDK、代码模板、基准 Bot、练习工具和示例回放。向 Portal 提供基板元素图例、规则图解的短回放、基准 Bot 策略说明及 `arena-replay/2` 回放示例。
